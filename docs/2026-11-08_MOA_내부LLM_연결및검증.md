# MOA 내부 LLM 연결 및 검증

## 설계 결론

MOA → Kubernetes 내부 agent-service → 중앙 LLM 연결관리에서 선택한 모델 순서로 호출한다. 모델 주소·자격증명·호출 동시성·대체 모델은 기존 중앙 설정을 사용한다. MOA에 외부 API 키를 복사하지 않는다. 브라우저는 MOA 서버에만 접속한다.

- LLM_PROVIDER=custom
- OPENAI_BASE_URL=http://agent-service.bbb-namespace.svc.cluster.local:8000/api/v1
- MOA_LLM_PROXY=1
- OPENAI_MODEL 미설정: 중앙 프록시의 현재 기본 모델을 따른다.
- OPENAI_API_KEY 미설정: 현재 내부 프록시에는 별도 클라이언트 키가 필요하지 않다. 업스트림 키는 프록시에서 관리한다.

현재 기능은 관리자용 문서 질의다. 파일 편집·셸 명령·Claude 도구 실행을 제공하지 않는다. 기존 자체 로그인과 Keycloak 로그인 권한 검사는 그대로 사용한다. 회원에게 채팅 권한을 자동 부여하지 않는다.

## 동작과 제한

프로젝트 최상위 md/mdx 문서를 이름순으로 최대 12,000자까지 참고한다. 문서 경로는 허용 폴더 안의 실제 경로로 제한하며 심볼릭 링크 문서는 제외한다. 전체 문서를 모두 읽는 검색 시스템은 아니므로 대규모 문서 검색은 별도 개발 대상이다.

프록시에 interactive 우선순위로 비동기 제출하고 같은 내부 호스트에서 결과를 조회한다. 대기 중 15초마다 연결 유지 이벤트를 보낸다. 답변 본문은 생성 완료 후 표시한다. 총 대기 제한 10분, 입력 8,000자, 출력 최대 2,048토큰이다. 같은 대화의 중복 요청과 4개를 초과하는 MOA 동시 요청은 거절한다. 실패는 성공으로 표시하거나 자동 재제출하지 않는다.

중지는 MOA의 대기와 결과 표시를 중단한다. 중앙 프록시에 이미 제출된 작업은 계속 수행될 수 있다. 프록시 취소 API가 없어 GPU 작업 중단까지 보장하지 않는다.

성공한 대화는 nfs-hdd PVC의 /data/llm-sessions.json에 저장한다. 최대 최근 100개 대화, 대화별 40개 메시지, 요청에는 직전 20개 메시지를 사용한다. 파일 권한 0600과 원자적 교체를 적용한다. 기존 구조와 같이 단일 파드/프로세스가 전제다. 관리자 사이의 대화 이력은 공유되므로 민감한 개인 대화용으로 사용하지 않는다.

## 작업 절차

1. MOA 파드에서 agent-service DNS/HTTP와 큐 응답 확인.
2. 연결 코드·권한·이력·문서 경로 제한 테스트 및 로그인 보안 회귀 테스트, Next 빌드.
3. 컨테이너 빌드, 사설 레지스트리 push, 이미지 digest 고정.
4. 기존 Secret/PVC를 유지하고 Deployment의 LLM 설정과 이미지 변경. Recreate 전략으로 짧은 중단 발생 가능.
5. 파드 준비 및 HTTPS 확인. 임시 관리자/회원 계정을 만들어 실제 로그인·채팅·후속 대화·권한 차단 검증. 테스트 계정과 대화는 종료 후 삭제.
6. 결과를 문서에 기록하고 main에 push.

## 되돌리기

이전 이미지 digest와 Deployment 설정을 적용한다. LLM_PROVIDER, OPENAI_BASE_URL, MOA_LLM_PROXY 환경변수를 제거하면 기존 Claude CLI 경로로 돌아간다. 이전 이미지는 Claude CLI가 설치되어 있지 않아 채팅은 사용할 수 없지만 문서 조회와 로그인은 유지된다. PVC와 인증 Secret은 삭제하지 않는다.

## 검증 결과

- 새 단위 테스트 5개 통과: OpenAI 요청 형식, 큐 조회 호스트 고정·오류 전파, 빈 응답 실패, 문서 범위 제한, 대화 저장·이어가기·동시 요청 제한.
- 기존 OIDC 보안 테스트 14개 통과.
- Next.js 프로덕션 빌드 통과.
- 운영 배포 이미지: `sha256:08e053c50bf7022b99e66dc4bf4927958f54464021417989ae27936f90083d86`. 파드 1/1 Running, 재시작 0, 외부 HTTPS 로그인 200.
- 중앙 활성 모델 확인: `gemma-4-E4B-it-MLX-8bit`, `http://192.168.219.48:8000/v1`, fallback 없음.
- 재부팅 완료 후 기존 내부 주소가 복구됐다. `/v1/models`의 미인증 요청은 401로 응답하며, MOA는 중앙 프록시에 보관된 인증 설정을 사용해 실제 생성에 성공했다. 주소나 전역 모델 설정, API 키 변경은 필요하지 않았다.
- 실제 운영 채팅: 문서 요약 277자 생성(19,892ms), 같은 대화 후속 답변 110자 생성(9,168ms). 사용 모델명과 프록시 주소가 실제 설정과 일치함을 확인했다.
- 추가 후속 질문도 실제 모델 서버 주소 `http://192.168.219.48:8000/v1`로 정확히 답했다(58자, 66,480ms; 기존 배치 작업과 큐 공유에 따른 대기 포함).
- 실제 대화 ID: `llm-abec4319-f96a-456c-b351-4913e9bfe789`. 질문 3개·답변 3개, 총 6개 메시지의 서버 이력 복원 확인.
- `MOA 운영 기록` 프로젝트에 실제 연결 설정과 실제 생성 응답 보고서를 저장했다. MDX 렌더링 HTTP 200 확인: https://moa.delvrio.com/p/moa-operations/llm-verification
- 검증용 임시 계정은 삭제했으며 실제 대화·보고서 데이터는 PVC에 유지했다. 실제 사용자 비밀번호·쿠키·API 키는 출력하지 않았다.
- 초기 실패 원인은 모델 서버 업그레이드·재부팅 중 네트워크 단절이었다. 재부팅 중 503/504가 발생했고 MOA는 실패를 성공으로 표시하지 않았다. 회원 채팅 403 차단과 각 검증 종료 후 임시 계정 삭제도 확인했다.
